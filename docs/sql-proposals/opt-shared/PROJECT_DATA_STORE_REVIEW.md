## Store/recovery
project_data_store_REVIEW.sql creates a private append-only metadata table, RLS enabled and forced, no policies or app-role grants. No operational tables or historical evidence are updated. UPDATE/DELETE/TRUNCATE on the metadata table are rejected by a trigger.

recover_project_data_reviewed is SECURITY INVOKER with EXECUTE revoked from PUBLIC/anon/authenticated/service_role; execute only through an explicitly authorized owner-maintenance session (the executing owner must possess appropriate RLS-bypass privileges). It accepts1–20 reviewed entries in one transaction, limits bytes/rows, computes SHA256 from original PDF bytes, checks document and manifest identity under a document lock, validates complete structured metadata, and inserts only metadata. Identical document/data/extractor replay returns duplicate; conflicting data or extractor provenance rejects. PDF bytes are not stored by this proposal. Owner input is trusted reviewed extraction, not browser output; matching PDF hash alone never proves extraction correctness. The extractor fingerprint must correspond to the reviewed source and its independently checked result.

## Visibility decision — deliberate absence, not a new permission
No existing exact Project-data-row-to-authorized-order relationship has been established. Piece counts, profile identity, same reservation somewhere in the document and order substrings are NOT sufficient proof: one full printed reference may name many lines/orders. Recovery intentionally stores no automatic disclosure grant.

The proposed ungranted sgp_opt_resumen_project_data_review_v1 adapter delegates document selection to the existing authenticated/scoped summary reader, joins sidecar metadata on exact document/PDF/manifest identity and preserves old summaries/status. It ALWAYS omits optional projectData pending an approved association contract, including removing an inline projectData value so it cannot bypass review. An owned document reports ASSOCIATION_NOT_AUTHORIZED or NOT_PERSISTED; unowned documents never appear. This is a safe read-compatible preparation, NOT a working data-disclosure feature. No production consumer was rewired and no new EXECUTE grants were added.

Important integration gate: the UI/extractor patch's current path accepts inline projectData through the old reader. Do not activate that producer/reader combination with complete references until the same visibility gate is enforced. Simply adding optional data to an existing full-document summary response would expand the disclosed content. The existing old profile/material visibility is preserved by the adapter; it does not imply permission to disclose Project data references.

Decision needed to enable detail: establish an authoritative, complete association for EVERY order/line named by each row, with immutable source-row provenance and fresh scope checks; or explicitly authorize a separate full-document reference-visibility policy. That is a permission/data-contract decision, not a string parsing heuristic. Until then keep omission. Do not fabricate positive authorization fixtures and call that proof of real mapping.
